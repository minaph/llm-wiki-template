# LLM Wiki — Engineering Starter

`llm_wiki/` は、人間とLLMがソフトウェアプロジェクトの要求・設計・検証結果を理解し、更新し続けるための汎用スターターである。IssueやPull Requestが扱う実装・納品と連携し、通常の開発工程からこぼれやすい設計理由、未検証事項、再検討すべき判断を記録する。

このスターターにはプロジェクト固有の知識や実行結果を含めない。導入先の資料を確認して、要求・設計・検証のひな型を記入する。

```text
llm_wiki/
├── README.md       # 入口と記録先の使い分け
├── TODO.md         # 人間が要望を書き、現在状態を確認する入口
├── TASK_SYSTEM.md  # Taskの形成・2Slot+E・選択・実行方法
├── WRITING.md      # 文章の品質基準
├── SKILL.md        # エージェント向けの入口
├── wiki/           # 要求・設計・結果・判断・実践知
├── tasks/          # 作業の目的・内容・完了条件
├── runs/           # 実行ログ、作業過程、実行単位の貢献主張
└── scripts/        # 検査などの再実行可能な処理
```

## 作業の進め方 — 2 Work + E

標準の一回の起動では、二つの独立した実作業 `Work 1 / Work 2` と、一つの独立品質管理 `Slot E` を閉じる。二つのWorkは課題系列への局所集中を抑え、Slot Eは今回の作業対象から外れたWiki領域を継続的に再読して内部品質を保つ。

1. **READMEとTODOを読む。** 作業方法を決める前に、このREADMEと [TODO](TODO.md) をその都度読み直す。新しい要望、優先度変更、完了したのに未更新の項目があれば現在状態へ反映する。
2. **Work 1を選ぶ。** 人間からの直接依頼があればWork 1へ置く。そうでなければTODO、[Task一覧](tasks/README.md)、期限、事業影響、不確実性、最後の確認時期から最も価値の高い作業を選ぶ。
3. **Work 2を独立に選ぶ。** Work 1の直前成果をそのまま続けるのではなく、選択可能なTaskとTODOをもう一度見て、別の問い・根拠面・判断差を持つ作業を選ぶ。最近実行されていない重要領域、異なる種類の根拠、異なるClient Needを考慮する。
4. **各Workの完了条件を満たす。** 対象Taskをその都度読み直し、目的、一次資料、必要な行為、品質基準、停止・引継ぎ条件まで進める。コード等から直接確認したこと、推論、実行した検証、クライアントが確認したことを区別する。
5. **Slot Eで別のWiki Entryを点検する。** [Wiki内部品質の独立点検](tasks/wiki-editorial-quality.md) を実行し、Work 1 / Work 2で新設・実質改稿・中心参照した文書や同じ判断系列を原則避ける。現在の作業から離れた既存Wiki Entryを通読し、中心claim、根拠、適用範囲、用語、構造、リンクを点検する。
6. **Run Noteに貢献を記録する。** Work 1、Work 2、Slot Eそれぞれについて、既存理解へ何を加え、変え、限定し、反証し、修復したかをRun-level contribution claimとして記す。二つのWorkを無理に一つの物語へまとめない。
7. **TODOを再読して閉じる。** Run Noteを書く前後にTODOを再確認し、今回状態が変わった要望を更新する。Taskを一回実行しただけで人間の要望全体が満たされていなければチェックを付けない。
8. **文章と参照を検査する。** 更新した文書を読み直し、完成時に `python3 llm_wiki/scripts/validate.py` を実行する。

P0相当の障害対応、安全上の緊急作業、利用可能な実行時間・権限が明確に不足する場合はWork 1を優先して停止できる。その場合はRun Noteに2Slot+Eを閉じられなかった理由と再開条件を書く。通常の忙しさだけを二枠目やEの省略理由にはしない。

## 2つのWorkの独立性

Work 1とWork 2は、Task IDが異なることだけを独立性の条件にしない。同じTaskを二枠で選ぶこともできるが、各枠が少なくとも **別の判別可能な問い、主な根拠面、判断差、停止条件** を持つことを確認する。同じ根拠を見出しだけ分けたり、Work 1の成果からWork 2の問いをその場で生成して直列工程にした場合は、一つのWorkの下位工程として扱う。

Work 2の選択では単純な回数均等化を目標にしない。短期集中には価値がある場合もあるため、`最近の露出 / 具体的な次の問い / 期待情報利得 / 開始コスト / 直前文脈からの再開しやすさ` を分けて見る。選択の偏りが繰り返される場合は [Task運用の点検](tasks/task-system-health.md) を使う。

## Slot E — Wiki内部品質の独立管理

Slot Eは `WIKI-EDITORIAL-QUALITY` に固定する。各Workが自分の成果物を読み直す責任は維持したうえで、Eは**関係の薄い別記事**を点検する。Work成果の二重チェックではなく、今回の作業だけでは放置されやすいWiki Entryへ定期的な再読機会を与えることが目的である。

長く再読されていない文書、参照されやすい文書、肥大化した文書、要求や実装の変更に記述が追いついていない可能性がある文書を優先できる。Eで大規模な設計再判断や実行検証が必要な問題を見つけた場合は、その場で憶測して直さず後続Taskとしての実施方法を検討する。

## TODO — 人間からの明示的要求

[TODO.md](TODO.md) は、人間が「何をしてほしいか」を直接書き、対応状況を短時間で確認するための窓口である。具体的な機能追加、修正、調査、優先度変更等を、観察・感想・一般知識とは分けて追跡する。

TODOとTaskは同じ状態機械ではない。TODOは人間の要求が満たされたかを追跡し、Taskはその要求を含む仕事をどう実行するかを定義する。一つのTODOを既存Taskへ接続してもよく、単発の検証Taskを形成してもよく、明確な直接作業ならTaskを増やさず処理してもよい。形成方法は [Taskの運用](TASK_SYSTEM.md) を参照する。

## 記録先の使い分け

### `wiki/` — 現在の理解と判断

要求、システム設計、設計判断、検証結果、実践知をまとめる。結果の成否や設計判断の理由は、Wikiを読むことで理解できるようにする。判断に必要な測定値、適用条件、失敗、未確定事項をRun Noteだけに残さない。

重要な事項には、コード、対象のコミットや版、原資料、Run Noteへの参照を付ける。詳細なログを本文から分けても、根拠をたどれるようにする。同じ説明を複数文書へコピーせず、正本を一つ決めてリンクする。

### `tasks/` — これから行う作業

Taskは、作業の目的・根拠・行為・完了条件を定めた文書である。`type` は検証やEditorial等の作業内容を表す。単発・常設などの存続形態と、終了・停止・再開条件は個別Taskの本文に書く。

検証実験もEditorial quality controlもTaskとして扱う。作成方法と項目の意味は [Taskの運用](TASK_SYSTEM.md) を参照する。

### `runs/` — 実行ログ、作業過程、実行単位の貢献

Run Noteは、一回の起動についてWork 1、Work 2、Slot Eを記録する。事後検証に必要な実行ログ・コマンド・環境・版・生成物への参照と、それぞれのTask実行が既存理解へ与えた知的差分を残す。

設計判断や反復利用する知識の正本はWikiへまとめる。Run Noteの貢献主張は「今回何を変えたか」を示し、Wiki Entryの中心主張は「現在何が成り立つか」を示すため、同じ文を二重にコピーする必要はない。

実行者の違いでディレクトリを分けず、実行者はRun Noteの冒頭に記録する。

### `scripts/` — 再実行可能な処理

検査、索引生成、移行などの処理を置く。初期版には文書の検査スクリプトと、その回帰テストを含める。

## Wiki Entry-level claim と Run-level claim

**Wiki Entry-level claim** は、後続者が再利用・支持・懐疑・改訂できる、現在の再利用可能な命題である。Wiki文書の中心主張として根拠、適用範囲、反例、未検証事項と接続する。一つの文書に異なる根拠や反証条件を持つ複数の中心命題がある場合は、必要な範囲で番号を付け、個別に指し示せるようにする。

**Run-level contribution claim** は、一つの独立Task実行が既存状態へ与えた知的差分である。「ファイルを更新した」ではなく、「どの既存理解に対して、何を追加・限定・反証・実行確認・品質修復したか」を記述し、可能なら対象のWiki Entry-level claimへリンクする。

ファイルが参照されたこと、後続作業で使われたこと、支持されたことは、それだけで主張の妥当性を証明しない。同じRun内で自分が自分の主張を支持しても後続評判の証拠にはしない。参加者順位や評判点数は作らず、後続のSUPPORT / CHALLENGE / 改訂 / 再利用は、命題がどう作用したかを追跡する材料として扱う。

## Run Noteのメタデータ

Run Noteでは `run_id / task / executor` を必須とする。`task` は複雑なYAML配列にせず、**カンマ区切りの一行文字列として複数Taskを明示的に列挙できる**。

標準2Slot+EではWork 1、Work 2、Slot Eの順に、たとえば次のように書く。

```yaml
task: direct-request, DESIGN-MAINTENANCE, WIKI-EDITORIAL-QUALITY
```

同じTaskをWork 1 / Work 2の両方で独立した作業として実行した場合は同じIDを二回書ける。緊急停止等で一部だけ実行したRunは、実行したTaskだけを列挙し、本文で省略理由を書く。`direct-request` はTask Entryを持たない直接依頼を表す特別値である。

## 用語と文書構造

- **Task文書**：一つの作業を定義するファイル。Task Entryとも呼ぶ。
- **Work**：2Slot+Eの一つの実作業枠。各Workは独立に検査できる問いと成果を持つ。
- **Slot E**：`WIKI-EDITORIAL-QUALITY` を実行し、Work 1 / Work 2から離れたWiki Entryを独立に点検する品質管理の枠。
- **Wiki文書**：再利用する理解をまとめたファイル。Wiki Entryとも呼ぶ。
- **Run Note**：Work 1 / Work 2 / Eの実行証拠と、各Taskの貢献主張を残す文書。
- **正本**：同じ事項を複数箇所に書く場合に、更新と参照の基準にする文書。
- **メタデータ**：ファイル冒頭の `---` で囲んだ項目。作業内容・状態などの短い情報を記す。

説明は本文に書き、メタデータは必要最小限にする。初期版は手動でTaskを選ぶため、自動割当用の `registry.json` は同梱しない。将来導入する場合の扱いは [Taskの運用](TASK_SYSTEM.md) に記す。

新しいディレクトリは、更新周期、更新者・権限、機械処理、規模や探しやすさに実質的な違いが生じた場合に検討する。概念が異なるという理由だけで文書の置き場所を増やさない。

## 導入

1. [TODO](TODO.md) を人間の要望入口として共有する。
2. [要求のひな型](wiki/client-needs.md) を導入先の要求へ置き換える。
3. [システム設計のひな型](wiki/system-design.md) に現在の主要構成と、維持すべき動作・互換性の条件を書く。既存の `docs/` 等がある場合は事項ごとに正本を決め、参照で結ぶ。
4. [標準Task](tasks/README.md) を確認し、Work用Taskのうち不要なものは `status: paused` にする。`WIKI-EDITORIAL-QUALITY` は標準Slot Eとして維持する。
5. `CODE-DESIGN-REDISCOVERY` を一度実行し、暗黙の設計と未検証事項をWikiへ記す。
6. [文章の品質基準](WRITING.md) に沿って読み直し、文書の検査を実行する。

プロジェクトルートの `AGENTS.md` 等には、「継続的な設計・検証・コード再点検を行う前に `llm_wiki/README.md` と `llm_wiki/TODO.md` を読む」と記せばよい。

## コミットメッセージ

ユーザーの直接指示によらない通常のLLM Wiki更新をコミットする場合は、コミットメッセージの先頭に必ず `wiki:` を付ける。例：`wiki: 設計判断の根拠を更新`。ユーザーの直接指示に基づく更新には、この接頭辞を必須としない。 詳細は[Taskの運用](TASK_SYSTEM.md#コミットメッセージ)を参照する。

## 検査の範囲

検査は完成時に行い、参照切れと必須メタデータの記入不足をエラーにする。下書き用の例外は設けない。配布用の `_TEMPLATE.md` は実際のTaskやRunとして数えないが、リンクは検査する。

Git管理情報の `.git` はディレクトリ構成の検査と文書の探索から除外する。Git worktreeの `.git` ファイルも検査対象にしない。

検査対象は、Markdownのインラインリンクと参照形式リンクのローカル参照先、IDの重複、Task・Runの必須メタデータ、スターターのディレクトリ構成である。Wiki外のコード・資料へのローカルリンクも検査する。外部URLの到達性、見出しアンカー、本文中の未記入箇所、主張の正しさは検査しない。汎用スターターの要求・設計のひな型が残っていても検査は通るため、成功を導入完了や内容の正しさの証明にしない。

メタデータは各項目を一行で記す。`required_capabilities` は `[code-read, doc-edit]` のような空でないリストを使い、Run Noteの `task` だけは `TASK-A, TASK-B, WIKI-EDITORIAL-QUALITY` のようなカンマ区切り複数列挙を許容する。それ以外は空でない文字列とし、複雑なYAML構造や複数行の値は使わない。

空白や複雑な括弧を含むパスは、リンク先を `<...>` で囲む。Markdownのコード例やコメント内のリンクは検査対象にしない。Run Noteの `task` は各要素をtrimし、すべてが実在するTask IDまたは `direct-request` であることを検査する。重複IDは、同じTaskを二つのWorkで使う正当な場合があるため許容する。

検査スクリプトを変更した場合は、`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s llm_wiki/scripts -p 'test_*.py'` で回帰テストを実行する。
