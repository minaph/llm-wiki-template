# LLM Wiki — Engineering Starter

`llm_wiki/` は、人間とLLMがソフトウェアプロジェクトの要求・設計・検証結果を理解し、更新し続けるための汎用スターターである。IssueやPull Requestが扱う実装・納品と連携し、通常の開発工程からこぼれやすい設計理由、未検証事項、再検討すべき判断を記録する。

このスターターにはプロジェクト固有の知識や実行結果を含めない。導入先の資料を確認して、要求・設計・検証のひな型を記入する。

```text
llm_wiki/
├── README.md       # 入口と記録先の使い分け
├── TASK_SYSTEM.md  # Taskの作成・選択・実行方法
├── WRITING.md      # 文章の品質基準
├── SKILL.md        # エージェント向けの入口
├── wiki/           # 要求・設計・結果・判断・実践知
├── tasks/          # 作業の目的・内容・完了条件
├── runs/           # 実行ログと作業過程の振り返り
└── scripts/        # 検査などの再実行可能な処理
```

## 作業の進め方

1. **依頼と現在の状態を確認する。** 人間からの直接の依頼を優先する。継続作業を選ぶ場合は、[Task一覧](tasks/README.md) と対象のTask文書を読む。
2. **今回の範囲と完了条件を確認する。** 対象Taskをその都度読み直し、目的、一次資料、必要な行為、品質基準、停止・引継ぎ条件を確認する。会話や過去の実行記録だけから推測しない。
3. **必要な能力を持つ実行者を選ぶ。** 資料の読解で答えられる問いと、シェル・テスト・測定などが必要な問いを分ける。権限や実行環境が足りない場合は、条件を明記して引き継ぐ。
4. **問いに答えるための確認を行う。** コード等から直接確認したこと、推論、実行した検証、クライアントが確認したことを区別する。実行が目的のTaskは、計画の作成だけでは完了しない。
5. **結果をWikiにまとめ、実行経緯をRun Noteに残す。** 結果・適用条件・解釈・設計判断はWikiへ記す。生ログ、再現手順、作業過程の振り返りはRun Noteへ置き、相互に参照できるようにする。必要な後続作業はTaskや[作業候補](tasks/proposals.md) に記録する。
6. **文章を読み直し、検査する。** 更新した文書の整合性と読みやすさを確認し、完成時に `python3 llm_wiki/scripts/validate.py` を実行する。

## 記録先の使い分け

### `wiki/` — 現在の理解と判断

要求、システム設計、設計判断、検証結果、実践知をまとめる。結果の成否や設計判断の理由は、Wikiを読むことで理解できるようにする。判断に必要な測定値、適用条件、失敗、未確定事項をRun Noteだけに残さない。

重要な事項には、コード、対象のコミットや版、原資料、Run Noteへの参照を付ける。詳細なログを本文から分けても、根拠をたどれるようにする。結果の詳細を設計文書に書く場合、検証一覧からその文書へリンクし、同じ説明を重複して保守しない。

### `tasks/` — これから行う作業

Taskは、作業の目的・根拠・行為・完了条件を定めた文書である。`type` は検証などの作業内容を表す。単発・常設などの存続形態と、終了・停止・再開条件は個別Taskの本文に書く。

検証実験もTaskとして扱う。作成方法と項目の意味は [Taskの運用](TASK_SYSTEM.md) を参照する。

### `runs/` — 実行ログと作業過程の振り返り

Run Noteは、一回の作業について、事後検証に必要な実行ログ・コマンド・環境・版・生成物への参照と、進め方の振り返りを残す文書である。設計判断や検証結果の説明はWikiへまとめ、Run Noteから参照する。

試行錯誤から得た知見も、今後の実装・検証・運用で再利用する価値が高ければWikiへ整理する。実行者の違いでディレクトリを分けず、実行者はRun Noteの冒頭に記録する。

### `scripts/` — 再実行可能な処理

検査、索引生成、移行などの処理を置く。初期版には文書の検査スクリプトと、その回帰テストを含める。

## 用語と文書構造

- **Task文書**：一つの作業を定義するファイル。Task Entryとも呼ぶ。
- **一回の作業**：今回選んだ範囲について、確認・記録・必要な引継ぎまで行う単位。常設Taskでは繰り返し実施する。
- **Wiki文書**：再利用する理解をまとめたファイル。Wiki Entryとも呼ぶ。
- **正本**：同じ事項を複数箇所に書く場合に、更新と参照の基準にする文書。
- **メタデータ**：ファイル冒頭の `---` で囲んだ項目。作業内容・状態などの短い情報を記す。

説明は本文に書き、メタデータは必要最小限にする。初期版は手動でTaskを選ぶため、自動割当用の `registry.json` は同梱しない。将来導入する場合の扱いは [Taskの運用](TASK_SYSTEM.md) に記す。

新しいディレクトリは、更新周期、更新者・権限、機械処理、規模や探しやすさに実質的な違いが生じた場合に検討する。概念が異なるという理由だけで文書の置き場所を増やさない。

## 導入

1. [要求のひな型](wiki/client-needs.md) を導入先の要求へ置き換える。
2. [システム設計のひな型](wiki/system-design.md) に現在の主要構成と、維持すべき動作・互換性の条件を書く。既存の `docs/` 等がある場合は事項ごとに正本を決め、参照で結ぶ。
3. [標準Task](tasks/README.md) を確認し、不要なものは `status: paused` にする。
4. `CODE-DESIGN-REDISCOVERY` を一度実行し、暗黙の設計と未検証事項をWikiへ記す。
5. [文章の品質基準](WRITING.md) に沿って読み直し、文書の検査を実行する。

プロジェクトルートの `AGENTS.md` 等には、「継続的な設計・検証・コード再点検を行う前に `llm_wiki/README.md` を読む」と記せばよい。

## 検査の範囲

検査は完成時に行い、参照切れと必須メタデータの記入不足をエラーにする。下書き用の例外は設けない。配布用の `_TEMPLATE.md` は実際のTaskやRunとして数えないが、リンクは検査する。

検査対象は、Markdownのインラインリンクと参照形式リンクのローカル参照先、IDの重複、Task・Runの必須メタデータ、スターターのディレクトリ構成である。Wiki外のコード・資料へのローカルリンクも検査する。外部URLの到達性、見出しアンカー、本文中の未記入箇所、主張の正しさは検査しない。汎用スターターの要求・設計のひな型が残っていても検査は通るため、成功を導入完了や内容の正しさの証明にしない。

メタデータは、各項目を一行で記す形式に限定する。`required_capabilities` は `[code-read, doc-edit]` のような空でないリスト、それ以外は空でない文字列とする。複雑なYAML構造や複数行の値は使わず、詳細は本文へ書く。

空白や複雑な括弧を含むパスは、リンク先を `<...>` で囲む。Markdownのコード例やコメント内のリンクは検査対象にしない。Run Noteでは `run_id / task / executor` を必須とし、`task` が実在するTaskのIDか、直接依頼を表す `direct-request` かを確認する。Taskのstatusは個別に定義できるため、空値は検出するが未知の状態名は一律に禁止しない。

検査スクリプトを変更した場合は、`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s llm_wiki/scripts -p 'test_*.py'` で回帰テストを実行する。
